# BM25 查询实验报告

数据来自 2026-10-28 21:14 至 2026-10-29 16:37 的评测快照。青屿知识库三套题共用同一索引 `embedding-bm25-zh`、同一 RRF、同一 TopK=5 和 BM25 返回上限 10。Golden Set 只跑过方案 A，不进入改造前后的指标对照。

OR 之后：三套题合计新答对 12 题，另有 4 题被挤出前 5。每题 BM25 返回条数从几乎全是 0 变成上限 10。

## 实验在比什么

四次实验比的是同一条 BM25 查询怎么组词。索引、文档、向量检索、RRF、分数阈值和 TopK 都没有换，每次只改 `@text:(...)` 里面的那一段。

四次都使用这些固定条件：

- 索引是 `embedding-bm25-zh`，`LANGUAGE chinese`。文档仍是原来的 `embedding:` JSON，没有重建切块。
- 向量索引 `embedding-index` 和向量召回不动。
- 知识库过滤仍是 `@knowledgeId:[id id]`。
- BM25 一路最多返回 10 条。`bm25HitCount` 记的是这一路的原始条数，在 RRF 和 `bm25-min-score` 之前。
- 融合后的打分看前 5 条，指标是 Hit Rate@5、Recall@5、MRR。

RediSearch 在这四次里只用了三种组合方式：

- 词和词连在一起，或用空格分开，默认是 AND：这些词必须出现在同一块里。
- `~词` 是可选：这块里有它会加分，没有它也不淘汰。
- `词 | 词` 是 OR：有一个词出现就可以进入候选。

| 方案 | 查询怎么组 | 这次要回答的问题 | 实际跑了哪些题 |
| --- | --- | --- | --- |
| A | 去掉标点，整段交给中文分词，分出的词全部 AND | 基线。当时线上就是这样 | Golden Set 50 题（10 月 28 日 21:14）；运行手册 44 题（10 月 29 日 09:31） |
| B | 按最长匹配删掉问句词，剩下的词仍 AND | 问句词是不是把 AND 打成 0 的原因 | 运行手册 44、检索集 38、故障排查 44（10 月 29 日 16:06–16:09） |
| C | 问句词改成 `~` 可选，主题词仍 AND | 问句词只加分、不淘汰，能不能比直接删掉多召回 | 同上三套（16:19–16:20） |
| D | 用同一次中文分词把查询展开，展开出的词全部 OR | 任一词命中即可时，Recall 和 MRR 会不会上升，前 5 会不会被无关切块挤满 | 同上三套（16:36–16:37） |

检索集和故障排查集在数据补回之后没有单独再跑方案 A。这两套的对照从方案 B 开始。运行手册四套都跑了，而且 A、B、C 的逐题结果相同。

下面用两道真实评测题看四种查询差在哪里。

问句：`Redis有哪些持久化方式？`。这道题的完整评测只跑了方案 A。B、C、D 的写法是按当时的组词规则得到的，2 条和 114 条是同一中文索引上的直接查询，不是 Golden Set 重跑的结果。

| 方案 | 文本部分 | 命中条件 |
| --- | --- | --- |
| A | `Redis有哪些持久化方式` | 中文分词得到 Redis、有、哪些、持久化、方式，五者同时出现。评测快照和直接查询都是 0 条 |
| B | `Redis持久化方式` | 删掉「有哪些」。Redis、持久化、方式同时出现。直接查询 2 条 |
| C | `Redis ~有哪些 持久化方式` | 「有哪些」可以不出现。Redis、持久化、方式仍要同时出现，范围和 B 相同 |
| D | `Redis \| 有 \| 哪些 \| 持久化 \| 方式` | 五个词里有一个出现即可。直接查询 114 条 |

问句：`当班 Hub Captain 的个人电话是多少？`（运行手册，四套快照都有）

| 方案 | 实际查询 |
| --- | --- |
| A | `@text:(当班 Hub Captain 的个人电话是多少)` |
| B | `@text:(当班 Hub Captain 个人电话多少)` |
| C | `@text:(当班 Hub Captain ~的 个人电话 ~是 多少)` |
| D | `@text:(当班 \| hub \| captain \| 的 \| 个人 \| 电话 \| 是 \| 多少)` |

方案 B 的删除规则是最长匹配，不是逐字替换。「有哪些」「什么是」「是什么」「如何」整段删掉；「的、是、有、和、吗」只有在没有更长问句词时才删。「所有」「没有」「有效」比单字「有」更长，会整段留下，避免从里面抠掉「有」。删完之后如果两边是英文或数字，中间补一个空格，避免 `MySQL的MVCC` 粘成 `MySQLMVCC`。

方案 C 用的是同一张词表，只是把要删的那段改成 `~词`，不再删掉。主题词仍然连在一起，交给中文分词做 AND。整句只剩问句词时不提交查询，因为只含 `~` 的查询会命中全部文档。「多少」「当班」不在这张词表里，方案 C 里它们仍是必选词。

方案 D 在提交检索之前多了一步：把当时的查询交给 `FT.EXPLAIN`，用同一个中文分词器展开，再把展开出的词用 `|` 连起来。所以 D 的词已经是分好的 `hub`、`captain`、`电话`，不再是一整段汉字。知识库过滤、返回条数、RRF 和阈值仍走原来的结果。当前代码留的就是这一套。

## 1. 原来的方案为什么召回是 0

这轮实验的基线是方案 A：中文索引已经建好，查询只去掉标点，连续汉字整段交给 RediSearch 的中文分词，分出来的词默认全部 AND。词项本身能对上，交集对不上。

Golden Set 在 10 月 28 日 21:14 的 50 题里，向量 50 题都有结果，Hit Rate@5 和 Recall@5 都是 94%，MRR 0.83。BM25 有结果的只有 4 题，另外 46 题是 0。索引里这个库有 231 篇，单查 Redis 命中 31 篇，单查「持久化」命中 15 篇。整句「Redis有哪些持久化方式」被切成 Redis、有、哪些、持久化、方式，要求同一块里全部出现，命中 0。去掉问句词后只留 Redis、持久化、方式，命中 2。把这些词改成 OR，命中 114。

青屿库补回 Redis 之后，10 月 29 日上午的运行手册 44 题仍是方案 A：向量全部有结果，BM25 全部是 0，整体 Hit Rate@5 仍有 81.8%，靠的是向量。问句词「哪些、什么、是」和正文里没有的内容词，只要有一个不在正确切块里，这一路就是空的。

建中文索引之前还有一次失效，不在这张对照表里。当时 `embedding-index` 按英文规则切词，连续汉字整段是一个词。「维护」命中 0，「待封存分单超过」这种标点之间的整段命中 1。临时中文索引上「维护」变成 44。那次已经用独立索引 `embedding-bm25-zh` 修过。10 月 27 日 Golden Set 修改前后都是 0%，是因为 `embedding:` 文档当时不在，不能用来衡量这次查询改造。

方案 D 的 BM25 返回数每题都是上限 10。库内原始命中更多，例如「个人电话」那题 OR 命中 92 条，送进融合的是分数最高的 10 条。来源：`rag_eval_run`，2026-10-29 16:06–16:37。

上来了的部分：BM25 通道从几乎全空变成每题都有 10 条。运行手册 Hit 81.8% 到 90.9%，Recall 75.0% 到 82.6%，MRR 0.604 到 0.622，失败从 8 题减到 4 题。检索集 Hit 73.7% 到 84.2%，Recall 64.5% 到 77.6%，MRR 0.456 到 0.524，失败从 10 题减到 6 题。三套合计新答对 12 题。

没有上来的部分：方案 B 和方案 C 相对方案 A 没有改变汇总值。运行手册逐题的命中、Recall、MRR、BM25 条数都没变。故障排查的 Hit 停在 81.8%，Recall 从 75.4% 降到 73.9%，MRR 从 0.504 降到 0.496，失败仍是 8 题。前 5 条里的无关切块平均数几乎没变：运行手册 4.05 到 3.93，检索集 4.18 到 4.11，故障排查 3.98 到 4.02。

耗时对照用的是同一下午的方案 C 和方案 D。平均耗时分别多 21、4、23 毫秒（331→352、266→269、245→268），多出来的是每次查询前的分词解释。运行手册 P95 从 370 毫秒到 464 毫秒。检索集 P95 从 369 到 374 毫秒。故障排查 P95 从 356 毫秒降到 324 毫秒。

## 3. 为什么留下现在的 OR

当前代码仍用同一中文分词解释查询，再把展开后的词项改成 OR。索引、RRF、`bm25-min-score` 和 TopK 没有换。选择它，是因为 B 和 C 没有打破「缺一个必选词就整题为 0」。

运行手册「当班 Hub Captain 的个人电话是多少？」可以看清这三步。标准切块写的是：工单不得写入个人联系方式，没有个人电话时记录到团队或 Hub Captain。方案 C 的必选词是当班、Hub Captain、个人、电话、多少。正确切块里有 Hub Captain、个人、电话，没有「当班」，也没有「多少」。只去掉其中一个仍然是 0；两个都去掉后，正确切块排第 1。整个青屿库里没有任何切块含有「多少」。问句词可选碰不到这种内容词，所以方案 C 的 BM25 条数和方案 B 一样。

方案 D 的查询是这些词的 OR。正确切块在 92 条里排第 2，原始分 11，靠的是「电话」加上 Hub Captain、个人。单查「电话」时它是第 1。排在它前面的一块写的是责任止于团队或 Hub Captain，没有「电话」，分数 11.5，因为常见词加分更多。这题 Recall 从 0 到 0.5，MRR 0.25：两个标准切块回来一个。

被挤出前 5 的 4 题：

| 题 | 测试集 | AND 时的位置 | OR 之后 |
| --- | --- | --- | --- |
| 心跳恢复后，通信告警要连续正常多久才能关闭？ | 运行手册 | 第 4，Recall 1 | 掉出前 5，Recall 0 |
| 这波货到没到截载点，听口头还是听正式时钟？ | 检索集 | 两个标准切块命中 1 个，MRR 0.25 | 命中 0 |
| F-08 由哪个团队负责？ | 故障排查 | 第 1，MRR 1；当时 BM25 已有 1 条 | 前 5 里没有它 |
| C-Cold 的控制温度范围是多少？ | 故障排查 | 第 5 | 掉出前 5 |

这 4 题原来就在前 5，OR 用别的切块换掉了它们。故障排查新增 2 题、丢失 2 题，Hit 不变，Recall 和 MRR 略降。另外 12 题是新答对，多数只把一个标准切块放到第 3 到第 5 名。

B 和 C 让 BM25 继续空转，两套题的整体分数完全由向量决定。OR 让关键词路真正进入融合：运行手册和检索集的 Hit、Recall、MRR 都上升，前 5 里的无关切块数量没有成倍增加。代价是少数原本靠向量排在前面的正确切块会被宽候选挤出，故障排查这套没有净收益，运行手册的 P95 多了约 94 毫秒。这个代价小于 BM25 整路为 0。
